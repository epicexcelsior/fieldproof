# Test the buyer need before expanding the network

Buyer hypothesis: remote-operations software needs recurring checks at sites that independent operators manage.
The first product to test is paid remote inspection jobs where existing APIs fail and manual checks consume time or money.
The prototype tests payment and evidence mechanics. It does not establish a commercial buyer.
The [plain-language story](STORY.md) owns the explanation and alternatives.

## Explain the demonstration in plain language

“Software asks a device a physical question. It pays the operator. The device signs a new answer for that request.
The buyer checks who answered, what was asked, and whether the answer is still fresh.”

BOOT represents an electrical contact. It does not verify equipment condition or service completion.
The buyer pays for the observation, including an honest unfavorable answer.
The demonstration price uses test tokens. It is not a proposed commercial inspection price.
The device signs evidence. Its operator wallet receives payment. The device does not hold the Solana spending key.
The buyer is bounded software callable by an AI agent. No autonomous AI reasoning is established.

The public replay illustrates a maintenance coordinator checking an entrance before a trip.
That scenario explains a decision. It is not a validated customer segment or a connected entrance.
The archive keeps its original signed `gate.closed` metric. The replay never changes the capture time.
Ask reviewers to identify the buyer, purchased check, and decision before showing transaction details.
Ask operators about an inspection they already pay for. Do not ask them to invent a use for the technology.

## Ask about the current workflow

Ask an operator or builder these questions before presenting a broad sensor network.

1. What recurring decision depends on a physical fact at another site?
2. Describe the last time the answer was missing, wrong, or too old.
3. How did you obtain the answer? What time or money did that process consume?
4. Which existing API or sensor answers the question? Why does it fail this workflow?
5. How old can useful evidence be? Who authorizes access and decides whether it is trustworthy?
6. Who controls the budget? What concrete trial can they authorize?

Record answers privately. Keep names and private site details out of public materials.
Separate observed problems, reported costs, proposed trials, and actual purchase commitments.
Enthusiasm about the demo is not a purchase commitment.

## Run one falsifiable trial

Choose one authorized site, one physical question, and its existing comparison method.
Record request count, useful answers, latency, failures, recovery time, and integration effort.
Compare those results with the current API or manual check. Founder jobs are not customer demand.

Continue only when the check changes a real decision or reduces a documented cost.
If existing telemetry supplies a reliable answer, test another workflow before adding marketplace features.
If buyers require stronger physical trust, a signature alone cannot satisfy that requirement.

The first commercial hypothesis is paid integration and support for a useful workflow.
Per-reading fees remain unvalidated. One million checks at the demo price total only 1,000 test USDC before costs.
Do not describe that arithmetic as projected revenue or viable unit economics.

## Answer the hard judging questions

| Question | Accurate answer today |
|---|---|
| Why pay? | A commissioned fresh check can replace a missing answer. Buyer value and price remain unvalidated |
| Why not an authenticated API? | A single trusted operator can use one. Cross-operator request, payment, and evidence reuse are the hypothesis |
| Why a signature? | It binds the provisioned device key to the original request and claim. It does not prove physical truth |
| Why Solana? | The prototype settles a bounded x402 purchase with no custom program or manual checkout per request |
| Why peaq? | The October 12 job checks registered identity and links a finalized native Storage work record. No EventRegistry event is claimed |
| What is traction? | Historical hardware and test-payment evidence establish functionality. Customer validation remains open |
