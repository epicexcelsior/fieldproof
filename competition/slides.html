FieldProof

Software pays for a fresh physical check.

The device signs its answer. The buyer verifies who answered and whether the answer is still fresh.

Working prototype: ESP32-C6 and Solana Devnet.

01 / A device signature authenticates a claim. It does not establish physical truth.

A remote inspection before a decision

Target workflow

An operator pays someone to check a physical fact at another site.

Its software lacks a reliable answer from an existing API.

FieldProof proposal

Commission one check from a device already on site.

Get a new answer tied to that request.

Value test: does the check replace a manual check or change a costly decision?

02 / Buyer hypothesis. No customer or willingness to pay is validated. Use an existing API when it supplies the answer.

What the prototype does

1. Request a check

The buyer fixes the contact question, device key, price, and ten-second age limit.

2. Pay the operator

Solana x402 settles 0.001 test USDC before measurement.

3. Measure and sign

The ESP32 reads the physical input and signs a new answer for this request.

4. Verify and decide

The buyer verifies the source, request, signature, and age before its next action.

03 / OPEN and CLOSED both fulfill the paid check. The operator wallet receives test tokens. The buyer's next action is separate.

The evidence has limits

The buyer can verify

This approved device signed the answer to this request.

An old answer fails the age policy. An edited answer fails signature verification.

The physical demonstration

Release or hold BOOT. The contact changes between OPEN and CLOSED.

The contact does not prove contents, safety, or completed work.

04 / BOOT is a contact stand-in. No robot or real entrance is connected. The software buyer can serve an AI agent.
