The first buyer hypothesis

An automation builder needs a current reading from equipment at another location. The equipment belongs to another operator.

FieldProof tests a small purchase between those parties. A contact check is the first capability. The board's BOOT input represents that contact.

The business question remains open: does a paid fresh check improve an existing workflow enough to justify another integration?

Try it in one minute

  1. Open Inspect today's paid check.
  2. Select Verify original. Expect a valid signature, expired evidence, and WAIT.
  3. Select Flip contact state. Expect signature rejection.
  4. Restore Verify original.
  5. Select Show full page. Select Verify buyer payment for a read-only Devnet query.

The original timestamp never changes. A payment cannot make an old reading fresh.

What this prototype establishes

Working and demonstrated

A fresh real-device reading followed a real Devnet test payment. The independent query verified the 1,000-base-unit transfer.

The buyer limits spending and accepts a configured device key. It rejects modified evidence and preserves uncertain operations for review.

The signature binds a device claim to a request. It does not prove truthful sensing, enclosure contents, or equipment safety.

The peaq path

The intended peaq role is portable provider identity and a job-linked activity record. The buyer will check the registered device key before payment.

The adapters and controlled tests exist. Live machine activation and an independently readable activity event remain pending.

This demo's payment runs on Solana. It claims no live peaq identity, customer traction, or commercial revenue.
